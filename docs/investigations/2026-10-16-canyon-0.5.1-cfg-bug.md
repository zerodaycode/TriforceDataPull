# Canyon-SQL 0.5.1 panics on insert and count

Date: 2026-10-16

## Symptom
With `canyon_sql = { version = "0.5.1", features = ["postgres", "migrations"] }` (like the docs say), the app panics on the first insert:

```
thread 'main' panicked at src/dao/models/leagues.rs:6:24:
Reached the panic match arm of insert for the DatabaseConnection type
```

The build also shows this warning on every entity:

```
warning: unexpected `cfg` condition value: `postgres`
  = note: using a cfg inside a derive macro will use the cfgs from the destination crate
          and not the ones from the defining crate
```

## Why tables are created and one row is inserted anyway
- The migrations run inside the Canyon crates, compiled with their own `postgres` feature, so they work.
- The generated `insert()` runs the `INSERT` through Canyon code too, so the row is written.
- After that, the generated code in our crate reads the returned id with a `match` whose Postgres arm was removed by `cfg`. Only `_ => panic!()` is left, so it panics. Every failed run leaves one row.

`find_all()` works because `CanyonMapper` puts the `cfg` in the right place.

## Root cause
Some generators in `canyon_macros` 0.5.1 put `#[cfg(feature = "...")]` inside `quote!`, so it ends up in our code:

| Generated method | `cfg` arm | Fallback |
|---|---|---|
| `insert` / `insert_datasource` | `query_operations/insert.rs:59` | `insert.rs:85` `panic!("Reached the panic match arm of insert ...")` |
| `multi_insert` / `multi_insert_datasource` | `query_operations/insert.rs:304` | `insert.rs:338` `panic!()` |
| `count` / `count_datasource` | `query_operations/select.rs:154` | `select.rs:169` `panic!()` |

Same for the `mssql` / `mysql` arms. `lib.rs:448` and `lib.rs:552` (`CanyonMapper`) do it right: the `cfg` is outside `quote!`, so it is checked when `canyon_macros` is compiled.

## Workaround
Declare the features in our crate and forward them:

```toml
[features]
default = ["postgres"]
postgres = ["canyon_sql/postgres"]
mssql = ["canyon_sql/mssql"]
mysql = ["canyon_sql/mysql"]
```

Tested: `League::count()` panics without it and returns `Ok` with it (PostgreSQL 18.6). Removing the block brings the panic back.

## Status in newer branches
On `main` and `develop` the `cfg` is outside `quote!` and the panic arms are gone, so the bug is fixed there. We moved to `develop`, see [ADR 0001](../decisions/0001-use-canyon-sql-develop-branch.md).

## Report for upstream

> **`CanyonCrud` panics on every insert/count in 0.5.1**
>
> With `canyon_sql = { version = "0.5.1", features = ["postgres"] }` and no `[features]` in the user crate, `insert()` and `count()` panic with `Reached the panic match arm of insert for the DatabaseConnection type`. The INSERT is executed before the panic.
>
> Cause: `query_operations/insert.rs:59`, `insert.rs:304` and `select.rs:154` put `#[cfg(feature = "...")]` inside `quote!`, so it's evaluated in the user crate. The user crate has no `postgres` feature, so only the `_ => panic!()` arm is left.
>
> Fix: build those arms with `#[cfg]` outside `quote!` like `lib.rs:448` does. It looks fixed on `main`/`develop`, can a release with it be published?
>
> Workaround: declare `postgres = ["canyon_sql/postgres"]` as a default feature in the user crate.
